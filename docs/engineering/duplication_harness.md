# Duplication Harness

This document explains the repository duplication harness:
- what it checks
- when to run it
- how to interpret the report
- how to record reviewed acceptable duplicates

Use this document when the question is:
- should I run duplication detection for this change?
- what does the duplication report mean?
- what is actionable debt vs acceptable parallel structure?
- how do I add an allowlist entry?

Use `docs/engineering/agent_pr_loop.md` for the broader delivery workflow.

## Why This Exists

Agent-generated code tends to duplicate small helpers, mappings, translations,
and local workflow tails.

That duplication often passes tests and static checks while still making the
codebase worse over time.

The duplication harness exists to make this maintainability debt visible during
self-review instead of relying on reviewer memory.

## What The Harness Is

The duplication harness is a two-layer setup:

1. `jscpd` finds raw duplicate code blocks
2. the internal `tool/filter_duplication_report.dart` helper turns raw clone output into a
   repository-specific review signal

This repository intentionally does **not** use raw clone output directly.
The filter narrows the output to the duplicate classes that matter here.

## Profiles

The harness currently has three separate profiles.

Note:
- the full verification pipeline now runs the core profile and the small-helper
  profile by default
- the broader presentation profile remains opt-in because it still represents a
  higher-noise review signal

### 1. Core profile

Command:

```bash
dart run mobile_core_kit_cli:mobilekit duplication check --profile core
```

Purpose:
- non-presentation maintainability duplication
- shared logic duplication
- feature/data/domain/runtime duplication that tends to drift silently

Current scan scope:
- `lib/features`
- `lib/core/foundation`
- `lib/core/runtime`
- `lib/core/infra`
- `lib/navigation`

Config:
- `.jscpd.json`
- `tool/duplication_allowlist.json`

Current categories:
- `failure_mapper`
- `bridge_translation`
- `model_translation`
- `workflow_tail`
- `parser_helper`
- `formatter_helper`
- `normalization_helper`

Typical examples:
- `ApiFailure -> AuthFailure`
- `AuthFailure -> SessionFailure`
- repeated `toSessionEntity()` / `toTokensEntity()` conversion logic
- repeated “fetch current user after success” tails
- repeated `tryParse...`, `fromString...`, trim/null/default wrappers

### 2. Small-helper profile

Command:

```bash
dart run mobile_core_kit_cli:mobilekit duplication check --profile small-helpers
```

Purpose:
- small local helper duplication
- especially helper-shaped duplication that agents tend to introduce repeatedly
- especially date/label/message/format/field-error helpers

Config:
- `.jscpd.small_helpers.json`
- `tool/small_helper_duplication_allowlist.json`

Current categories:
- `field_error_helper`
- `display_helper`
- `formatter_helper`
- `parser_helper`
- `normalization_helper`

Typical examples:
- `_firstFieldError(...)`
- `_formatDate(...)`
- `_labelForStatus(...)`
- `_messageForMediaPickException(...)`
- `_normalizeContentType(...)`

### 3. Presentation profile

Command:

```bash
dart run mobile_core_kit_cli:mobilekit duplication check --profile presentation
```

Purpose:
- narrow Flutter presentation duplication detection
- focused on high-value presentation repetition
- intentionally separate from the core profile

Config:
- `.jscpd.presentation.json`
- `tool/presentation_duplication_allowlist.json`

Current categories:
- `cubit_field_validation`
- `cubit_failure_handling`
- `form_page_section`
- `display_helper`
- `micro_widget`

Important:
- this profile is **not** broad widget-tree similarity detection
- it is intentionally narrow
- it exists to catch repeated presentation helpers and form workflow patterns
  without turning all UI similarity into noise

## When To Run It

Run the duplication harness when the change is likely to introduce or reshape
shared logic.

Good triggers for the **core profile**:
- extraction or consolidation refactors
- new mappers, parsers, formatters, or normalization helpers
- adapter/bridge changes
- repository/use-case cleanup prompted by repeated patterns
- code generated by agents that added multiple similar helpers

Good triggers for the **presentation profile**:
- repeated auth/account form work
- repeated cubit validation or failure handling
- repeated page sections or page-local UI helpers
- new small presentational widgets that look very similar to existing ones

Good triggers for the **small-helper profile**:
- new private helper functions in pages, widgets, or cubits
- repeated date/label/message/display formatting
- repeated `_firstFieldError(...)`-style helpers
- repeated normalization/parsing helpers that are too small to stand out in the
  broader duplication profiles

You do **not** need to run duplication detection for every tiny change.
Treat it as a high-signal self-review tool for structural repetition.

## How To Read The Report

The report separates duplicate groups into two buckets.

### Actionable duplicate groups

These are open maintainability debt.

They mean:
- the detector found a duplicate pattern in a category the repo cares about
- the duplicate has not been explicitly reviewed and accepted
- it deserves human judgment

Actionable does **not** automatically mean “extract this now.”
It means “review this now.”

### Reviewed acceptable groups

These are duplicate groups that were reviewed intentionally and recorded in an
allowlist with rationale.

They remain visible in the report so the acceptance is explicit.
They do **not** count as open duplication debt anymore.

This is important:
- acceptable duplication must be explicit
- acceptable duplication must not live only in reviewer memory

## How To Review A Duplicate Group

For each duplicate group, decide:

1. Is this true maintainability debt or intentional parallel structure?
2. If it is debt, where should the shared code live?
   - feature-local helper
   - feature-root shared utility
   - `lib/core/**`
3. If it is acceptable, what is the reason?
4. Is the current category label accurate enough?

Use these heuristics:

### Usually real debt
- repeated failure mapping
- repeated bridge translation between vocabularies
- repeated parser/formatter/normalization helpers
- repeated workflow tails
- repeated cubit validation/failure helpers

### Often acceptable
- parallel page composition across related auth forms
- DTO pairs representing distinct backend contracts
- parallel domain value objects with different domain meaning

## Allowlists

The harness supports reviewed acceptable duplicates through JSON allowlists.

Core profile:
- `tool/duplication_allowlist.json`

Small-helper profile:
- `tool/small_helper_duplication_allowlist.json`

Presentation profile:
- `tool/presentation_duplication_allowlist.json`

Each entry records:
- `firstPath`
- `secondPath`
- `category`
- `reason`
- `reviewedOn`
- `status`

Example:

```json
{
  "firstPath": "lib/features/auth/data/model/remote/auth_response_model.dart",
  "secondPath": "lib/features/auth/data/model/remote/auth_result_model.dart",
  "category": "model_translation",
  "reason": "Distinct backend contracts and distinct user DTO types; shared token/session conversion alone is not worth forcing a common DTO abstraction.",
  "reviewedOn": "2026-04-19",
  "status": "reviewed_acceptable"
}
```

## When To Add An Allowlist Entry

Add an allowlist entry only when:
- the duplicate group was reviewed intentionally
- the duplication is acceptable for now
- the reason is concrete and defensible

Do **not** use the allowlist to hide unresolved debt.

Bad reasons:
- “too hard right now”
- “looks fine”
- “agent generated it”

Good reasons:
- distinct backend contracts
- intentional parallel workflows
- shared abstraction would reduce clarity
- repeated page structure is design-system-driven and not yet worth generic UI
  scaffolding

## What The Harness Does Not Do

The duplication harness does **not**:
- decide architecture for you
- automatically refactor duplicates
- understand semantic intent perfectly
- replace code review
- make every duplicated line a bug

It is a self-review and reviewer-support tool.

## Workflow Placement

Recommended use:
- run the harness during self-review when the change touches shared or repeated
  patterns
- expect the core profile and small-helper profile to run during
  `dart run mobile_core_kit_cli:mobilekit verify --env dev`
- review the output before opening/updating the PR
- if a duplicate is acceptable, record it explicitly
- if it is debt, either fix it now or call it out as follow-up debt

This is intentionally **not** a default hard CI gate.
The value is in surfacing maintainability debt at the right time, not in adding
another blunt failing check.
